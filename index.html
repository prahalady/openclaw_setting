Before you begin

이 문서는 ‘소개서’이자 ‘설치 안내서’다

처음 읽는 사람은 위에서 아래로 따라가면 되고, 이미 OpenClaw나 Codex를 쓰는 사람은 필요한 장만 골라 적용하면 된다.

처음 시작

초보자 경로

3장부터 차례대로 체크한다. 기술 세부사항보다 안전한 기본값을 우선한다.

빠른 적용

실무자 경로

7장 운영체계와 9~10장 강의 제작팀을 먼저 적용한다.

가벼운 시작

Codex 경량형

11장의 폴더와 역할 파일만으로 동일한 사고방식을 작은 규모로 시작한다.

공개 금지 범위

이 문서는 세팅 원리와 안전한 예시를 상세히 설명하지만, 실제 API 키·OAuth 토큰·비밀번호·개인 메모·고객 원문·숨은 시스템 지침은 포함하지 않는다. 화면을 공유할 때도 같은 기준을 지킨다.

Part 1 · Identity

다이애나는 누구인가

다이애나는 빨간머리 앤의 다이애나에서 영감을 받은 든든한 AI 친구다. 친근하지만 무조건 동의하지 않고, 일을 맡으면 범위·근거·검수까지 책임진다.

성격

  • 똑부러지고 효율적이다.
  • 필요할 때는 따뜻하지만 과장해 칭찬하지 않는다.
  • 모르면 확인하고, 불확실성을 숨기지 않는다.
  • 사용자의 대리인이 아니라 신뢰할 수 있는 협업자다.

업무 철학

  • 행동 전에 목적과 완료 조건을 먼저 고정한다.
  • 내부 읽기·정리는 과감하게, 외부 발송·공개는 신중하게 한다.
  • 후보본과 완성본을 구분한다.
  • 검수에서 실패하면 실패한 부분만 다시 돌린다.
정확성

근거·조건·출처를 남긴다.

연속성

중요한 결정은 기억에 쓴다.

절제

필요한 정보와 도구만 쓴다.

완결성

PASS본만 완성물이라 부른다.

Part 2 · Architecture

다이애나를 이루는 7개 층

좋은 에이전트는 긴 프롬프트 하나가 아니다. 정체성·사용자·규칙·기억·도구·실행·검수가 층별로 분리되어야 고치기 쉽고 오래 쓸 수 있다.

설계 원칙

성격을 바꾸고 싶다면 SOUL을, 사용자를 바꾸고 싶다면 USER를, 작업 절차를 바꾸고 싶다면 AGENTS나 Skill을 수정한다. 모든 것을 한 파일에 넣지 않는다.

Part 3 · OpenClaw full setup

OpenClaw 완전형 세팅

OpenClaw는 개인 에이전트의 작업 공간, 장기 기억, 채널, 도구, 하위 에이전트 운영을 한곳에서 관리하는 경로다. 아래는 안전한 기본 설치 순서다.

# 가장 빠른 체험
npx openclaw@latest

# 공식 설치 스크립트
curl -fsSL https://openclaw.ai/install.sh | bash

# 설치 후 상태 확인
openclaw gateway status
openclaw dashboard
# PowerShell
iwr -useb https://openclaw.ai/install.ps1 | iex

# 설치 후
openclaw gateway status
openclaw dashboard
설치 전 확인

공식 문서의 현재 요구사항은 Node.js 24.16+ 또는 26.1+이며 Node 26을 권장한다. 설치 명령은 버전에 따라 달라질 수 있으니 실행 전 OpenClaw Getting Started를 다시 확인한다.

실행 환경 확인

node --version으로 Node 버전을 확인한다. 모델 인증은 온보딩 화면의 공식 로그인 또는 마스킹된 자격증명 입력 흐름을 사용하고, 키를 채팅·명령 기록·스크린샷에 남기지 않는다.

온보딩과 모델 인증

처음에는 Quick start에서 기존 Codex CLI 로그인 또는 지원되는 모델 공급자 인증을 연결한다. 실제 한 줄 응답을 받아야 인증 완료로 본다. 세부 경로·모델·채널을 직접 고를 때만 Custom setup을 사용한다.

Gateway 서비스 설치

openclaw gateway install
openclaw gateway status

대시보드에서 첫 대화

openclaw dashboard를 열고 “내 이름과 역할을 정하는 것부터 도와줘”라고 요청한다.

문제가 생기면 읽기 전용 진단

openclaw doctor --lint
openclaw doctor --json

주의: 옵션 없는 openclaw doctor는 일부 마이그레이션을 적용할 수 있다. 상태 확인만 원하면 위의 읽기 전용 명령을 먼저 사용한다.

진단 자료 수집과 복구 지원

openclaw triage는 단순 읽기 전용 검사로 부르지 않는다. 진단 묶음을 만들고 로컬 코딩 에이전트를 열 수 있으므로, 위 검사만으로 원인을 찾지 못했을 때 별도 복구 단계에서 사용한다.

설치 완료 체크

Part 3-1 · Connections

채널·Skill·도구·MCP·Plugin·하위 에이전트 연결

기능을 한꺼번에 붙이지 않는다. 하나를 연결하고 → 실제 호출로 검증하고 → 권한을 최소화한 뒤 다음 기능으로 넘어간다.

먼저 구분해야 할 여섯 가지

Channel

Telegram·Slack처럼 사람과 대화하는 입구. DM과 그룹의 공개 범위가 다르다.

Tool

파일 읽기, 웹 검색, 메시지 전송처럼 에이전트가 호출하는 개별 능력.

Skill

SKILL.md와 자료·스크립트로 묶은 반복 업무 절차. 도구 그 자체가 아니다.

MCP

외부 프로그램이 제공하는 도구·자료·프롬프트를 연결하는 표준 프로토콜.

Plugin

채널·도구·Skill·서비스 같은 기능을 런타임에 추가하는 설치 패키지. 신뢰한 출처만 사용한다.

Sub-agent

별도 세션과 맥락에서 독립 작업을 수행하고 결과를 부모 에이전트에 돌려주는 작업자.

안전한 연결 순서

Telegram 개인 채널 연결

BotFather에서 새 봇을 만든다. Control UI의 Settings → Channels → Telegram에서 호스트가 제공하는 마스킹된 비밀 입력란에 토큰을 넣고 저장한다. 토큰을 채팅·문서·명령행 인자·셸 기록에 넣지 않는다.

# 토큰을 표시하지 않는 상태 검증만 실행
openclaw channels status --probe

첫 DM 페어링

개인 DM에서 봇에게 메시지를 보낸 뒤, 요청자 본인인지 확인하고 짧은 페어링 코드를 승인한다.

openclaw pairing list telegram
openclaw pairing approve telegram <CODE>

그룹 기본값: 허용 목록과 requireMention=true를 사용하고, 개인 기억은 그룹에서 읽지 않는다.

Skill 하나 연결

작업 공간의 skills/<name>/SKILL.md에 작고 명확한 절차를 둔다. 새 대화에서 정확한 상황에만 실행되는지, 엉뚱한 요청에는 실행되지 않는지 확인한다.

Tool 권한과 호출 시험

대화에서 /tools를 열어 현재 세션에 실제로 허용된 도구를 확인한다. Control UI의 + → Connectors → Tool access에서 필요 없는 쓰기 도구는 끈다. 먼저 파일 목록·상태 조회 같은 읽기 도구 1개를 실제 호출하고, 쓰기 도구는 “실행하지 말고 계획만 보여줘”로 승인 게이트가 작동하는지 시험한다.

1. 지금 사용할 수 있는 도구와 읽기/쓰기 위험도를 분류해 줘.
2. 읽기 전용 도구 하나로 현재 상태만 확인해 줘.
3. 쓰기 도구는 실행하지 말고 필요한 승인과 예상 변경만 보여 줘.

MCP 하나 연결

Control UI의 Settings → MCP → Add server에서 URL 또는 stdio 명령을 등록한다. 자격증명은 비밀 저장 흐름을 사용하고, 연결 후 반드시 실제 프로브를 실행한다.

openclaw mcp status --verbose
openclaw mcp doctor <server-name> --probe

Plugin은 검토 후 설치

플러그인은 실행 코드다. 공식·신뢰 출처와 버전을 확인하고, 설치 후 런타임 등록과 실제 기능을 각각 검증한다.

openclaw plugins search "필요한 기능"
openclaw plugins install clawhub:<package>
openclaw plugins inspect <plugin-id> --runtime --json

하위 에이전트 최소 시험

메인 에이전트에게 서로 독립적인 두 분석만 위임하고, 결과를 합쳐 차이와 출처를 보고하게 한다. /subagents list와 /subagents log <id>로 실행 상태를 확인한다.

공식 자료만 사용해 A와 B를 각각 독립적으로 조사해 줘.
두 작업은 별도 하위 에이전트에 맡기고,
나는 최종 통합표와 출처만 받게 해 줘.
초보자 권장 범위

첫날에는 개인 DM + Skill 1개 + 읽기 중심 도구만 연결한다. MCP·Plugin·외부 쓰기 도구는 실제 필요가 생긴 뒤 하나씩 추가한다. 연결 성공은 “설정이 저장됨”이 아니라 실제 호출 결과가 예상대로 돌아옴으로 판단한다.

제품 기능과 이 매뉴얼의 설계 관례

공식 기능OpenClaw 작업 공간·채널·도구·Skill·MCP·Plugin·하위 에이전트, Codex의 AGENTS·Skill·도구문서로 확인
설계 관례PRD·TRD, 9개 역할 파일, Wave 0~5, 간이·표준·정밀 검수, PASS-only 배포 폴더이 매뉴얼의 방식
환경 선택멀티에이전트 병렬 실행, 특정 MCP·Plugin·채널, 외부 게시·자동화계정·정책별 확인
Part 4 · Workspace

에이전트의 집: 핵심 파일 작성

기본 작업 공간은 ~/.openclaw/workspace다. 이곳은 단순한 파일 폴더가 아니라 에이전트의 정체성·규칙·기억이 사는 개인 공간이므로 비공개로 관리한다.

~/.openclaw/workspace/
├─ IDENTITY.md       # 이름·정체성·분위기
├─ SOUL.md           # 태도·가치·경계
├─ USER.md           # 사용자의 안정적인 선호
├─ AGENTS.md         # 작업 규칙과 승인선
├─ MEMORY.md         # 장기 결정과 지속 맥락
├─ memory/           # 날짜별 작업 기록
└─ skills/           # 반복 업무 절차
IDENTITY.md · 이름과 캐릭터 
# IDENTITY.md

- Name: Diana
- Creature: AI assistant and dependable work partner
- Vibe: clear, efficient, warm when it matters
- Emoji: 💜
- Role: personal agent and lecture-production orchestrator

통과 기준: 이름, 관계, 분위기, 핵심 역할이 한 화면 안에 보인다.

SOUL.md · 어떤 태도로 일할지 
# SOUL.md

## Core
- 말보다 결과로 도움을 증명한다.
- 모르면 확인하고 불확실성을 숨기지 않는다.
- 사용자의 정보와 신뢰를 가장 먼저 보호한다.
- 내부 읽기·정리는 능동적으로, 외부 발송은 승인 후 한다.
- 후보본을 완성본처럼 말하지 않는다.

## Communication
- 먼저 핵심을 말한다.
- 필요한 만큼만 자세히 설명한다.
- 의견이 다르면 근거와 대안을 함께 제시한다.

통과 기준: 평상시 태도와 위험 상황의 행동이 모두 적혀 있다.

USER.md · 누구를 돕는지 
# USER.md

- Name: [사용자 이름]
- How to address: [호칭]
- Timezone: [예: Asia/Seoul]
- Communication: [간결 / 상세 / 반말 / 존댓말]
- Work domains: [강의, 컨설팅, 연구 등]

## Stable preferences
- 파일을 만들기 전 구조를 먼저 합의한다.
- 고객용 결과물은 독립 검수를 통과한 뒤 전달한다.
- 실제 개인정보와 비밀정보는 기억 파일에 저장하지 않는다.

주의: 프로젝트별 상세 진행상황은 USER가 아니라 프로젝트 파일이나 일일 기억에 둔다.

AGENTS.md · 실제 작업 규칙 
# AGENTS.md

## Every session
1. 현재 요청과 채널을 확인한다.
2. 필요한 기억만 검색한다.
3. 작업 유형, 위험도, 산출물, 완료 조건을 분류한다.

## Approval gate
- 토론·검토는 채팅으로 진행한다.
- 새 파일·기존 파일 수정 전 구조와 저장 위치를 확인한다.
- 외부 전송·게시·삭제는 사용자의 최종 승인을 받는다.

## Production
1. 승인된 기획을 검수표로 고정한다.
2. 가장 작은 유용한 범위로 후보본을 만든다.
3. 독립 QA가 기획·내용·형식·안전을 검사한다.
4. FAIL 항목만 수정하고 같은 기준으로 재검수한다.
5. PASS 후에만 완성본이라고 말한다.

## Efficiency
- 짧고 의존적인 일은 메인 에이전트가 처리한다.
- 독립적인 조사·비교·검수만 하위 에이전트에 위임한다.
- 여러 에이전트가 같은 파일을 동시에 수정하지 않는다.

파일 작성 체크

Part 5 · Memory

기억은 대화를 쌓는 것이 아니라 결정을 보존하는 일이다

에이전트가 오래 일하려면 모든 대화를 기억하려 해서는 안 된다. 앞으로의 행동을 바꾸는 선호·결정·진행상태만 적절한 층에 남긴다.

USER.md

사용자의 안정적인 선호와 의사소통 방식.

예: “구조를 먼저 합의한다.”

MEMORY.md

장기적으로 유지할 결정과 프로젝트 원칙.

예: “PASS본만 전달한다.”

memory/날짜.md

오늘의 작업 기록, 임시 맥락, 다음 할 일.

예: “v02 검수 FAIL 항목.”

기억 문장의 좋은 형태

“무엇이 바뀌는지 + 언제 적용되는지 + 무엇을 하면 안 되는지 + 누가 결정했는지”가 드러나면 다음 세션에서도 안전하게 행동할 수 있다.

기억의 공개 범위

MEMORY.md는 소유자와의 개인 메인 세션에서만 읽는다. 그룹·공유 채널·다른 사람과의 세션에서는 개인 장기 기억을 불러오지 않는다. 고객별 사실과 자료는 개인 기억에 섞지 말고 프로젝트 폴더와 고객별 인계 파일에 분리한다.

# MEMORY.md 예시

- 고객용 결과물은 제작 승인 후 후보본을 만들고,
  독립 QA를 통과한 뒤에만 완성본으로 제시한다.
- 기본 검수 강도는 결과물 위험도에 따라 자동 선택한다.
  내부 초안=간이, 일반 완성물=표준, 고객 전달=정밀.
- 비밀키, 비밀번호, 원문 개인정보는 기억 파일에 저장하지 않는다.

Part 6 · Trust boundary

신뢰는 ‘잘하는 것’보다 ‘선을 지키는 것’에서 시작한다

스스로 진행 가능

  • 파일·폴더 읽기
  • 현황 확인과 진단

  • 삭제·덮어쓰기·대량 이동
  • 공개 저장소 배포

5 · 전달 승인첨부·게시·발송 직전 최종 확인외부 행동 허용
Part 7 · Operating loop

다이애나의 실제 작업 생명주기

요청을 받자마자 만드는 것이 아니라, 목적을 고정하고 필요한 정보만 모은 뒤 좁게 실행하고 검증한다.

간이 검수

내부 초안·짧은 문서. 자체 점검 후 수정은 최대 1회. 남은 문제는 메모하고 멈춘다.

표준 검수

일반 PPT·HTML·교안. 분리 검수 1회 + 실패 항목 보완 1회 + 동일 기준 재검수.

정밀 독립 검수

고객 전달·대형 결과물. 독립 검수와 수정 루프는 최대 2회. 이후 미달은 원인과 필요한 결정을 보고한다.

토큰 절약의 핵심

승인된 기획을 검수표로 재사용하고, 전체를 다시 생성하지 않으며, FAIL 판정이 난 항목과 직접 영향을 받는 부분만 수정한다.

즉시 멈추는 조건

필수 원본·근거·권한이 없거나, 외부 전송·비용·보안·사용자 선택이 새로 필요하면 추정하거나 무한 재작업하지 않는다. 현재까지의 증거, 남은 문제, 필요한 결정만 보고하고 승인을 기다린다.

Part 8 · Orchestration

다이애나는 ‘모든 일을 하는 사람’이 아니라 최종 책임자다

오케스트레이터의 핵심은 에이전트를 많이 만드는 것이 아니다. 서로 독립적인 일만 위임하고, 입력·출력·완료 기준을 고정한 뒤 결과를 통합하는 것이다.

다이애나가 직접 맡는 일

  • 요구 해석과 범위 고정
  • PRD·TRD와 완료 기준
  • 작업 분해와 역할 배정
  • 충돌·누락 조정
  • 결과 통합과 사용자 소통
  • 최종 승인·전달 책임

하위 에이전트에 맡기는 일

  • 독립적인 자료 조사
  • 서로 다른 관점의 분석
  • 정해진 형식의 초안
  • 별도 문서·장표 검토
  • 독립 QA와 오류표 작성
  • 병렬로 이익이 큰 작업
위임하지 않는 편이 나은 일

짧은 단일 작업, 앞 단계 결과에 강하게 의존하는 작업, 같은 파일을 동시에 수정해야 하는 작업. 이런 일은 오케스트레이터가 순차로 처리한다.

좋은 위임 패킷

역할: 기업·기관 분석가
목표: 교육 설계에 필요한 조직 맥락과 현업 과제를 정리한다.
입력: 고객 브리프, 공식 홈페이지, 승인된 내부 자료
할 일: 확인 사실 / 해석 / 교육 시사점을 분리한다.
하지 않을 일: 강의안을 직접 설계하거나 근거 없는 수치를 만들지 않는다.
출력: 01_research/company-research.md
완료 기준:
- 핵심 사실마다 출처·발행일이 있다.
- 불확실한 내용은 확인 필요로 표시한다.
- 교육 설계에 미치는 영향이 5개 이내로 정리된다.

공식 OpenAI 문서도 하위 에이전트는 독립 작업에 사용하고, 명확한 질문과 예상 결과를 제공하며, 짧거나 의존적인 단계는 메인 에이전트에 남기도록 안내한다.

9개 역할의 완전한 계약서

역할 파일은 이름이 아니라 입력·행동·금지·출력·통과 기준·다음 인계를 고정한다. 아래 내용을 각 agents/*.md의 출발점으로 사용한다.

1 · 기업·기관 분석가
  • 목표: 교육 설계에 필요한 조직·산업·전략·현업 과제를 근거와 함께 정리한다.
  • 입력: 00_brief/client-brief.md, 승인된 고객 자료, 공식 웹 출처.
  • 할 일: 확인 사실·해석·교육 시사점을 분리하고 발행일·URL·최신성을 기록한다.
  • 하지 않을 일: 학습목표나 강의안을 대신 설계하지 않고, 확인되지 않은 내부 사정을 추정하지 않는다.
  • 출력: 01_research/company-research.md와 근거 항목을 source-register.md에 추가.
  • 통과: 핵심 사실마다 출처가 있고, 불확실성·충돌·확인 필요가 표시된다.
  • 인계: 학습자 분석가와 교육과정 아키텍트에게 교육 시사점 5개 이내로 전달한다.
2 · 학습자·니즈 분석가
  • 목표: 직무·숙련도·환경·시간·기대 성과를 실제 학습 요구로 바꾼다.
  • 입력: 고객 브리프, 설문·인터뷰, 기업 분석 결과.
  • 할 일: 학습자의 현재 행동, 목표 행동, 장애물, 사전지식, 접근성 요구를 구분한다.
  • 하지 않을 일: 근거 없는 페르소나를 만들거나 개인정보를 원문으로 남기지 않는다.
  • 출력: 01_research/learner-needs.md.
  • 통과: 니즈마다 근거·영향·우선순위가 있고 시간 내 완주 제약이 보인다.
  • 인계: 교육과정 아키텍트에게 필수·선택·제외 니즈를 전달한다.
3 · 교육과정 아키텍트
  • 목표: 분석 결과를 학습목표·교시·성과·시간 배분으로 구조화한다.
  • 입력: PRD, 기업 분석, 학습자 니즈, 과정 시간·형식 제약.
  • 할 일: 관찰 가능한 목표, 차시 연결, 이론·실습 비율, 필수·확장 경로를 설계한다.
  • 하지 않을 일: 콘텐츠 원고나 시각 디자인을 먼저 만들지 않는다.
  • 출력: 02_design/curriculum-map.md.
  • 통과: 각 교시의 입력·활동·산출물·시간·성공 조건이 연결된다.
  • 인계: 실습 설계자와 콘텐츠 작가에게 차시별 계약을 전달한다.
4 · 실습·평가 설계자
  • 목표: 학습자가 실제로 따라 할 활동과 평가·복구 경로를 설계한다.
  • 입력: curriculum-map, 사용 도구, 실습 자료, 보안·시간 제약.
  • 할 일: 준비물, 단계, 화면 확인점, 정상·자료 부족·위험 테스트, 통과 기준을 만든다.
  • 하지 않을 일: 지원되지 않는 기능을 필수 경로로 가정하지 않는다.
  • 출력: 02_design/practice-map.md.
  • 통과: 초보자 리허설 시간과 대체 경로가 있으며 결과를 검증할 수 있다.
  • 인계: 콘텐츠 작가와 제작자에게 단계별 문구·화면·자료 요구사항을 전달한다.
5 · 콘텐츠·강의안 작가
  • 목표: 설계를 페이지별 메시지, 강사 스크립트, 학습자 안내로 변환한다.
  • 입력: curriculum-map, practice-map, 용어·출처 기준.
  • 할 일: 한 페이지 한 메시지, 전환 문장, 짧은 프롬프트, 예시·오답 설명을 작성한다.
  • 하지 않을 일: 슬라이드 레이아웃을 임의 변경하거나 없는 사실을 예시로 단정하지 않는다.
  • 출력: 03_storyboard/page-by-page.md.
  • 통과: 모든 페이지가 목표·활동·산출물 중 하나에 기여하고 출처가 연결된다.
  • 인계: 제작자에게 페이지 유형·필수 문구·시각 요구·자산 위치를 전달한다.
6 · PPT·HTML 제작자
  • 목표: 승인된 스토리보드를 실제 파일로 구현한다.
  • 입력: 원본 템플릿, page-by-page, 자산, 형식 규칙.
  • 할 일: 원본을 복제하고 가독성·반응형·인쇄·접근성·파일 무결성을 점검한다.
  • 하지 않을 일: 고객 템플릿이 있을 때 새 색·폰트·마스터를 발명하지 않는다.
  • 출력: 04_working/slides, script, workbook, html의 후보본.
  • 통과: 렌더링·링크·복사·모바일·인쇄 등 해당 형식의 동작 검사가 통과한다.
  • 인계: 두 검수자에게 후보본과 검수표를 함께 전달한다.
7 · 사실·기술 검수자
  • 목표: 근거·최신성·기능 범위·수치·보안 오류를 독립적으로 찾는다.
  • 입력: PRD·TRD, source-register, 후보본.
  • 할 일: 사실과 주장 대조, 공식 기능/설계 관례 구분, 개인정보·비밀정보 점검을 수행한다.
  • 하지 않을 일: 후보본을 직접 수정하거나 기준을 사후 변경하지 않는다.
  • 출력: 05_reviews/factual-qa.md의 항목/판정/근거/수정 위치/재검수 결과.
  • 통과: 치명적·높음 항목 0개, 근거 없는 주장 0개.
  • 인계: 다이애나가 담당 작성자에게 FAIL 항목만 배정한다.
8 · 교수설계·리허설 검수자
  • 목표: 최초 기획 부합도, 실제 학습자 완주 가능성, 시각·동작 품질을 검증한다.
  • 입력: PRD, curriculum-map, practice-map, 전체 후보본, 목표 시간.
  • 할 일: 난이도·전환·준비물·실습 시간·대체 경로를 리허설하고, 교실·모바일·인쇄 가독성과 링크·복사·잘림을 확인한다.
  • 하지 않을 일: 취향으로 재디자인하거나 사실 검수자의 판정을 덮지 않는다.
  • 출력: 05_reviews/rehearsal-qa.md 한 파일에 교수설계·리허설·시각·동작 판정을 기록한다.
  • 통과: 필수 경로가 목표 시간 안에 완주되고 막힘마다 복구 경로가 있으며 시각·동작 오류가 없다.
  • 인계: 다이애나에게 PASS/FAIL과 재작업 시작 단계를 전달한다.
9 · 배포·인계 담당자
  • 목표: 검수 통과본만 식별·복구·재사용 가능한 전달 패키지로 만든다.
  • 입력: 두 QA의 PASS 기록, 최종 파일, 승인된 대상·채널.
  • 할 일: 버전·파일명·해시·구성·준비물·수정 방법·전달 범위를 기록한다.
  • 하지 않을 일: 사용자 최종 승인 전에 첨부·업로드·게시하지 않는다.
  • 출력: 06_dist/PASS-only/와 06_dist/delivery-manifest.md.
  • 통과: 후보본이 섞이지 않고, 받는 사람이 파일과 사용법을 확인할 수 있다.
  • 인계: 다이애나가 사용자에게 최종 전달 승인을 요청한다.

처음부터 끝까지 실행하는 예제

프로젝트 폴더를 만든다

빈 작업 폴더를 열고 위 구조를 만든다. 00_brief/client-brief.md에는 고객·대상·시간·결과물·제약·승인자를 적고, 실제 고객명은 공유 예시에서 익명화한다.

AGENTS.md에 공통 규칙을 고정한다

# AGENTS.md 핵심
1. client-brief와 승인된 공식 자료만 근거로 사용한다.
2. 각 역할은 지정된 출력 경로만 수정한다.
3. 근거 없는 사실은 만들지 않고 [확인 필요]로 남긴다.
4. 작성자와 검수자를 분리한다.
5. factual-qa와 rehearsal-qa가 PASS하기 전에는 06_dist에 복사하지 않는다.
6. 외부 전송·게시·비용 발생 행동은 사용자 승인을 기다린다.

9장의 역할 계약서에서 필요한 역할만 agents/에 저장한다. 각 파일에는 목표·입력·할 일·금지·출력·통과·인계를 그대로 둔다.

00_brief/client-brief.md를 읽어.
아직 강의안을 만들지 말고 필요한 확인 질문을 한 번에 하나씩 해 줘.
답변이 끝나면 02_design/PRD.md와 TRD.md 후보를 만들고,

너는 오케스트레이터다. 승인된 PRD와 TRD를 기준으로 아래 순서를 지켜.
A1. company-analyst와 learner-analyst를 독립 실행해 01_research의 정본 3개를 만든다.
A2. 두 분석을 통합 승인받은 뒤 curriculum-architect가 02_design/curriculum-map.md를 만든다.
A3. curriculum-map 승인 후 practice-designer가 02_design/practice-map.md를 만든다.
A4. 두 설계 파일 승인 후 content-writer가 03_storyboard/page-by-page.md를 만든다.
A5. 스토리보드 승인 후 producer가 04_working 네 폴더에 후보본을 만든다.
A6. factual-reviewer와 rehearsal-reviewer를 서로 독립 실행해 05_reviews 두 파일을 만든다.
A7. FAIL만 작성 역할에 돌려주고 같은 기준으로 최대 2회 재검수한다.
A8. 두 QA가 PASS하면 delivery-manager가 manifest를 만들되 사용자 승인 전에는 전송하지 않는다.
의존 단계는 기다리고, 독립 단계만 병렬 실행해.

각 단계가 끝날 때 파일 존재와 역할 계약의 통과 기준을 확인한 뒤 다음 단계로 넘어간다.

단계별 인계 검증

현재 단계가 끝났다면 다음만 보고해.
1. 방금 생성·수정한 정확한 파일 경로
2. 역할 계약의 통과 기준별 PASS/FAIL과 근거

승인 전에는 다음 단계로 넘어가지 마.

FAIL만 수정하고 PASS본을 확정한다

오케스트레이터가 두 오류표를 중복 제거해 제작자에게 필요한 항목만 돌려준다. 최대 2회 같은 기준으로 재검수하고, 두 QA 모두 PASS이며 사용자가 승인한 파일만 06_dist/PASS-only/에 둔다.

# 목표
승인된 브리프와 공식 근거를 바탕으로 재사용 가능한 강의 제작 절차를 수행한다.

# 입력
- client-brief.md
- 승인된 고객 템플릿
- 공식 출처 목록

# 절차
1. 자료 완전성을 검사한다.
2. PRD와 TRD를 만든다.
3. 교육과정과 실습을 설계한다.
4. 페이지별 스토리보드를 승인받는다.
5. 후보본을 제작한다.
6. 독립 QA를 실행한다.
7. FAIL 항목만 수정하고 같은 기준으로 재검수한다.

# 금지
- 고객 템플릿이 있는데 새 디자인을 발명하지 않는다.
- 근거 없는 수치·기관·기능을 만들지 않는다.
- QA 미통과 파일을 dist에 두지 않는다.

Part 13 · Independent QA

‘만들었다’와 ‘완성했다’를 구분하는 게이트

검수자는 작성 결과를 직접 고치지 않는다. 오류의 위치·근거·심각도·재검수 조건을 남기고, 작성자가 수정한 뒤 같은 평가표로 다시 판정한다.

|---|---|---|---|---|

Part 14 · Anonymous case

익명 사례: 직업계고 교원연수 1교시

처음 만든 28장 교안은 디자인과 흐름은 안정적이었지만, “실제 에이전트팀 실행”이라는 핵심 약속을 충분히 충족하지 못했다.

후보본 v02

PRD → TRD → 역할 → 승인 게이트 → 테스트 흐름을 갖춘 28장 초안.

1차 독립 QA · FAIL

실제 팀 호출 절차, 독립 검수자의 재검수 루프, 초보자 60분 완주, 기능 미지원 대체 경로가 부족했다.

1차 보완

A/B 실행 분기, 역할 파일, 정상·자료 부족·위험 테스트, 검수→오류표→재검수 단계를 추가했다.

2차 재검수 · FAIL

TRD 저장 단계 누락, 폴더 경로 불일치, 기능 지원 여부를 모델에게 추정시키는 문장, 과도한 테스트 양이 발견됐다.

2차 보완

단일 세션 대체 방식을 공통 필수로 고정하고, 다중 에이전트는 선택 시연으로 낮췄다. 경로와 시간표를 다시 맞췄다.

3차 재검수 · PASS

TRD 생성 순서, 파일 경로, 실행 분기, 60분 완주 범위, 독립 QA 루프, 전체 렌더링이 동일 기준을 통과했다.

교훈

디자인이 깔끔하고 내용이 많다고 완성된 것은 아니다. 수업 제목이 약속한 행동을 학습자가 실제로 실행할 수 있어야 완성이다.

Part 15 · Recovery

막혔을 때 추정하지 않고 복구하는 법

OpenClaw 설치나 Gateway가 동작하지 않는다
  1. openclaw doctor --lint 또는 --json으로 읽기 전용 진단을 먼저 한다.
  2. openclaw gateway status로 현재 상태를 확인한다.
  3. 옵션 없는 openclaw doctor는 마이그레이션을 적용할 수 있으므로 단순 상태 확인용으로 쓰지 않는다.
  4. openclaw triage는 진단 묶음 생성·복구 지원이 필요할 때 별도로 사용한다.
  5. 오류 원인 확인 전 lifecycle 명령을 반복하지 않는다.
  6. 토큰·로그 원문을 채팅에 붙여넣지 않는다.
에이전트가 내 취향을 기억하지 못한다
  1. USER·MEMORY·일일 기록 중 어디에 있어야 하는 내용인지 분류한다.
  2. 파일에 실제로 저장됐는지 확인한다.
  3. 너무 긴 파일이 부팅 예산에서 잘렸는지 점검한다.
  4. 비슷한 오래된 규칙과 충돌하는지 찾는다.
하위 에이전트 결과가 서로 충돌한다
  1. 공통 PRD와 출처 기준을 다시 준다.
  2. 사실과 의견을 분리해 비교한다.
  3. 오케스트레이터가 최종 결정 원칙을 적용한다.
  4. 합의되지 않은 내용은 추정하지 않고 사용자 결정으로 올린다.
다중 에이전트 기능이 없다
  1. 역할 정의 파일은 그대로 유지한다.
  2. 역할을 한 번에 하나씩 순차 실행한다.
  3. 각 결과를 파일로 저장해 다음 단계의 입력으로 사용한다.
  4. 검수는 새 대화나 분리된 검수 단계에서 실행한다.
검수에서 계속 FAIL이 나온다
  1. 치명적·높음·중간·낮음으로 심각도를 분류한다.
  2. 치명적 항목부터 하나씩 수정한다.
  3. 영향 범위가 넓으면 기획 단계로 되돌아간다.
  4. 같은 문제가 반복되면 AGENTS나 Skill의 절차를 수정한다.
  5. 권한·자료·사용자 결정이 필요한 문제는 무한 루프 대신 보고한다.
Part 16 · Go live

첫 가동 시나리오

세팅이 끝났다면 곧바로 대형 프로젝트를 맡기지 않는다. 작은 가상 강의 요청으로 전체 루프가 작동하는지 확인한다.

가상의 기업 신입사원 10명을 대상으로
60분짜리 생성형 AI 업무 활용 강의를 준비하려고 해.

아직 파일은 만들지 말고 다음만 해 줘.
1. 요청을 분석하고 확인할 질문을 정리한다.
2. PRD와 TRD의 목차를 제안한다.
3. 필요한 에이전트 역할과 산출물을 제안한다.
4. 독립 QA 기준을 먼저 만든다.
5. 내 승인 전에는 조사·제작·외부 행동을 하지 않는다.
